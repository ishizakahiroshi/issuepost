# issuepost 設計文書

**まだ 1 行も実装していない。この文書が契約になる。** 先に書いているのは、4 本のアプリが
これに対して実装するからで、後から契約が動くと 4 本すべてに波及する。

**読む人**: 案件を送る側のアプリを書く人、台帳そのものを作る人、この形が自分のところに
合うか判断する人。**前提知識は要らない。** 組織ごとに変わる値はすべて設定に逃がしてあり、
ここに出てくるのはサンプルだけ。

**日時はすべて UTC**。サーバと全接続のタイムゾーンを UTC に固定する。
**守らないと「期限を過ぎた」の境界が、見る場所によって 1 日ずれる。**

**言葉**: 「案件」は起きたこと 1 件（不具合・要望・質問・メモ、またはアプリが自分で気づいた異常）。
「アプリ」は案件を送ってくる側のシステム。「台帳」は受け取って保管する 1 つのサービス。
「運営側」は台帳を動かしている自分たち。

---

## 原則

下のすべての判断は、この 4 つで決めた。**どこかが必要以上に複雑に見えたら、単純にする前に
ここと突き合わせる。**

1. **持ち主から直接もらう。** 案件の持ち主は、それが起きたアプリ。各アプリが自分の案件を
   自分で送る。**誰かが代理で集めて回る形（中継）は作らない。**
2. **効率は決め手にしない。** 実装量や行数の削減を理由に構成を決めない。
3. **可能な限りシンプルに。** 持ち主を 1 つにし、層を増やさない。持ち主が既にいるなら
   「中継を足さない」方向に、まだ決まっていないなら「1 か所にまとめる」方向に効く。
   **「何も作らない」という意味ではない。**
4. **台帳は保管する。加工しない。** アプリが送ってきたものを、そのまま保つ。
   書き換えたり分類し直したりした時点で、それは持ち主から来たものではなくなる。

ここから出てくる帰結が 2 つある。どちらも放っておくと崩れるので、先に書いておく。

- **台帳は、どのアプリのテーブルにも外部キーを張らない。** 利用者の表にも、組織の表にも、
  何にも張らない。**これが、台帳を後から別の場所へ動かせる理由そのもの。**
- **案件は消さない。** 子の表から親へ外部キーを張ってあるので、消せない形になっている。
  誤って出したものは状態で「対応しない」にして残す。**消せると、受入条件の「消えたことが残る」が
  行ごと消えて成立しなくなる。**
- **顧客は台帳を開かない。** 運営側の外にいる人は、いま使っているアプリの画面から案件を見る。
  アプリがサーバー同士で台帳から引く。**台帳のアカウントを配らないし、顧客ごとの台帳の分身も作らない。**

## 1. 表の形

### 1 つの表と、その軸

案件はすべて 1 つの表に入れる。異常検知・不具合・要望・質問の違いは**列**であって、
別のシステムではない。

これは容量の話ではない。**同じ表に入れないと存在しない数字がある。** いちばん効くのがこれ。
**質問が多く集まる画面は、壊れていない。分かりにくいだけ。** 不具合として直しても件数は減らない。
直すべきは画面の言葉か手順の案内。**質問と不具合が同じ表にいるときだけ、この区別が数字で出る。**

| 軸 | 識別子 | 値 | これで何が同じ表に入るか |
|---|---|---|---|
| 出どころ | `origin` | `human` ／ `detected` | 利用者の報告と、システムが自分で気づいた異常 |
| 種別 | `kind` | `bug` ／ `request` ／ `question` ／ `note` | **問い合わせ窓口を別に作らなくてよくなる** |
| 発生場所 | `place` | `screen_id` ／ `feature_id` ／ `environment` ／ `version` ／ `url` | 報告者が書かなくてもアプリが付ける |
| 指紋 | `fingerprint` | 失敗を表す安定したハッシュ | 検知した同じ異常がまとまる |
| 承認 | `approval_state` ／ `hold_until` | §2 の対応表 | 要望は判断を通してから開発へ流す |
| 関連 | `case_links` | `commit` ／ `doc` ／ `url` | **直した証拠がぶら下がる** |

**この表の日本語は説明であって、保存する値ではない。保存するのは識別子のほう。**
対応は §2 の「保存する識別子と、画面に出す言葉」にまとめてある。

### 項目

**実際のスキーマは `sql/0001_initial.sql`**（MariaDB）。**食い違ったら、下の項目表のほうが正しい。**

`cases` — 中心の 1 表。

| 項目 | 型 | 備考 |
|---|---|---|
| `id` | 内部 | 台帳の中だけの連番。誰にも見せない |
| `number` | 文字列 | **公開される案件番号。発行するのは台帳だけで、アプリは発行しない**（§3） |
| `source` | 文字列 | どのアプリから来たか。番号の接頭辞にもなる |
| `tenant_ref` | 文字列 | **1 本のアプリを複数の顧客が使うときの顧客の識別子**（§4）。分かれていないアプリは空 |
| `seq` | 整数 | `source` の中での連番。`number` は `<source>-<seq>` |
| `origin` | 列挙 | `human`（人が報告）／ `detected`（アプリが検知） |
| `kind` | 設定 | §2。サンプル: `bug` ／ `request` ／ `question` ／ `note` |
| `status` | 設定 | §2。**全員が同じ 1 セットを使う。**保存するのは識別子で、画面の言葉ではない |
| `approval_state` | 設定 | 承認が要る種別のときだけ意味を持つ |
| `title` | 文字列 | |
| `body` | 本文 | 人が書いた文、または検知した内容。**受け取ったまま保管する** |
| `reporter_ref` | 文字列 | **アプリが既に持っている、ただの識別子**（下記）。**`origin` が `detected` のときは空**（報告者がいない） |
| `screen_id` | 文字列 | アプリが付ける。報告者に選ばせない |
| `feature_id` | 文字列 | |
| `environment` | 文字列 | どの環境で起きたか。**番号には入れない** |
| `version` | 文字列 | |
| `url` | 文字列 | |
| `fingerprint` | 文字列 | `origin` が `detected` のときだけ入る |
| `promised_due` | 日付 | 報告した人に約束した期日（§2） |
| `hold_until` | 日付 | 保留の解除期限（§2） |
| `closed_at` | 日時 | **案件が終端状態になった日時。**添付の期限の起点（§6）。**最初から持つ** |
| `duplicate_of` | 参照 | まとめた先の案件を指す |
| `legacy_ref` | 文字列 | アプリ側が持っていた元の識別子。**送れば `(source, legacy_ref)` が一意になり、二重登録を防げる**（§3） |
| `created_at` / `updated_at` | 日時 | |

`case_number_sequences` — **番号の採番。**`source` ごとに 1 行だけ持ち、次に払い出す連番を入れる。
**発行するのは台帳だけ**（§3）。

`case_people` — **同じことに当たった人**。2 件目以降の報告は新しい案件を作らず、ここに 1 行足す。
**この人数が優先順位の根拠になる。** 4 人が止まっている件を 1 人の要望より先にやる、と言うには
数字が要る。

`case_events` — **状態と承認の移り変わり。追記だけで、上書きも削除もしない。**
`status` と `approval_state` は「いまの値」なので、変わると前の値が消える。
**4 本ぶんの経緯が集まると言う以上、経緯そのものを消さない。**却下の理由もここに残る。

`case_replies` — 報告した人へ何を返したか、いつ返したか。
**台帳に保存できたことと、相手に届いたことは別**なので、届いた日時を別に持つ。
案件について「送れなかったら送ったことにしない」と決めた以上、返信も同じ扱いにする。

`case_links` — `link_type`（`commit` ／ `doc` ／ `url`）と `ref`。
**コミットは、複製を持っている側が受け口へ送ってきたものをここへ保存する**（§3）。

`case_attachments` — 外部のファイル置き場への参照。**中身そのものは持たない。**
ファイルは台帳のデータベースにも、リポジトリにも入れない。どちらも際限なく膨らみ、
控えを取るのが重くなる。置き場は 1 つのアダプタ越しに扱い、**他を触らずに差し替えられるようにする。**

| 項目 | 備考 |
|---|---|
| `ref` | 置き場での参照。**実体が消えても空にしない**（§6） |
| `filename` | 元のファイル名 |
| `mime` | |
| `size_bytes` | |
| `sha256` | 内容のハッシュ。**実体が消えても残す。**同じものが後から来たときの判定がこれだけで成立する |
| `created_at` | 付けられた日時 |
| `deleted_at` | 実体が無くなった日時。無くなっていなければ空 |
| `deleted_reason` | `expired` ／ `removed_by_user` ／ `missing_at_store`（§6） |

索引は `(deleted_at, ...)` を持ち、**「まだ実体がある行」だけを安く絞れるようにする。**

`cleanup_runs` — **定期実行の記録。**いつ走って何件処理したかを残す。
受入条件に「定期実行が実際に動いていることを確認した」がある以上、**確認できるものが要る。**

### 報告した人は、ただの文字列

報告する人は、報告する時点で既にアプリへログインしている。**「誰がログインしていたか」の
持ち主はアプリ**なので、アプリが案件と一緒にその識別子を送る。**台帳が認証するのはアプリであって、
人ではない**（§4）。

`reporter_ref` はただの文字列で、アプリが既に持っている安定した識別子なら何でもよい。
外部キーは張らないし、台帳の中に利用者の表も作らない。**台帳がそれを氏名に解決できる必要も無い。**
画面に名前を出すのはアプリで、アプリはもともと名前を知っている。

これは意図的で、しかも効いている。**台帳が誰かの利用者テーブルと結合した瞬間に持ち出せなくなり、
原則 1 が静かに成り立たなくなる。**

## 2. 言葉の定義と設定

**業務固有の値をコードに書かない。** 種別・状態・承認状態は設定で定義する。
以下はサンプルであって、誰かが採用しなければならない既定値ではない。

### 保存する識別子と、画面に出す言葉

**保存するのは識別子。画面に出す言葉は表示名で、言語ごとに差し替える。識別子は翻訳しない。**

これは番号の接頭辞と同じ規則。接頭辞は保存したら永久に変えず、製品名が変わったら表示名だけを
変える。状態や種別も同じで、**`done` は保存された値、「完成」と `Done` はその見せ方。**

この分け方が無いと何が起きるか。**この文書を英語へ訳した人が「不具合」を `defect` と書き、
日本語を読んだ人が `bug` と書く。** 同じものに 2 つの値が入り、集計は静かに割れる。
**割れたことは、数字が合わなくなってから気づく。** 受け口の検査は識別子の一覧に対して行うので、
**一覧に無い値は最初から弾かれる**（それが検査できるのは、値が言葉ではなく識別子だから）。

| 日本語 | 保存する識別子 | English |
|---|---|---|
| **出どころ** | `origin` | origin |
| 人が報告 | `human` | reported by a person |
| アプリが検知 | `detected` | detected by the app |
| **種別** | `kind` | kind |
| 不具合 | `bug` | bug |
| 要望 | `request` | request |
| 質問 | `question` | question |
| メモ | `note` | note |
| **状態** | `status` | status |
| 未対応 | `new` | new |
| 調査完了 | `investigated` | investigated |
| 対応中 | `in_progress` | in progress |
| 完成 | `done` | done |
| 対応しない | `wont_do` | won't do |
| **承認状態** | `approval_state` | approval state |
| 承認不要 | `not_required` | not required |
| 承認待ち | `pending` | pending |
| 承認済み | `approved` | approved |
| 却下 | `rejected` | rejected |
| 保留 | `on_hold` | on hold |
| **関連の種類** | `link_type` | link type |
| コミット | `commit` | commit |
| 文書 | `doc` | document |
| 外部 URL | `url` | url |
| **期限 2 本** | | |
| 約束した期日 | `promised_due` | promised due date |
| 保留の解除期限 | `hold_until` | hold expiry |

**日本語の欄と English の欄は、どちらも表示名の候補であって正本ではない。正本は真ん中の列。**
上の状態の値はサンプルで、組織が別の 5 つを使うなら識別子ごと差し替えてよい。
**差し替えてよくないのは「識別子と表示名を混ぜること」のほう。**

### 状態の言葉は 1 セットだけ持つ

4 本のアプリから集めると、「どこまで進んだか」を表す言葉が何組も出てくる。業務側が使っている
もの、開発の作業を追うためのもの、受け皿の表が使っているもの。**1 組を選んで、入口で寄せる。**
後から揃えようとすると、**既に入っている全部の行を書き換えることになる。**

選ぶのは業務側が既に使っている組。**人が実際に読む画面に出る言葉だから。**

開発側の途中の状態（様子見・寝かせる、のような段階）は台帳に入れない。
**（承認の `on_hold`「保留」とは別物。**紛らわしいので、開発側のほうは「保留」と呼ばない）開発の作業を追っている側に
残す。**台帳が答えるのは「これは誰待ちか」であって、「担当者が今日の午後に何をしているか」ではない。**

### 期限は 4 つではなく 2 本

候補は放っておくと増える。対応予定日、保留の解除期限、開発側の作業の期日、報告した人に
約束した期日。**台帳が持つのは 2 本。**

- `promised_due` — 報告した人に伝えた期日。**どの画面でも「期限を過ぎた」はこれだけを指す。**
  候補が 4 つあると「遅れている」が答えられない
- `hold_until` — 保留の解除期限。**塩漬けになった案件が黙って消えないように**、期限が来たら浮いてくる。
  **浮いてくる場所は、顧客側と運営側の両方の一覧の先頭**（パネルは増やさない）

**`closed_at` は台帳が入れる。**`status` が設定の `terminal` に入った瞬間に記録し、
そこから外れたら（やり直しになったら）**空に戻す。**添付の寿命の起点なので、
やり直した案件の添付が消えかけたまま残らない。**これは加工ではなく、受け取った状態からの導出で、
元の `status` は書き換えていない。**

開発側の作業の期日は、開発の作業を追っている側に残す。

### 設定のサンプル

```toml
# サンプル。ここに出てくる値はすべて例であって、コードには 1 つも入っていない。

[kinds]
values = ["bug", "request", "question", "note"]
requires_approval = ["request"]

[statuses]
# 1 セットだけ。全アプリ・全画面がこれを使う。
values   = ["new", "investigated", "in_progress", "done", "wont_do"]
open     = ["new", "investigated", "in_progress"]
terminal = ["done", "wont_do"]      # ここへ入った瞬間に closed_at が入る
initial  = "new"                    # 受け口が新しい案件に入れる値
# 「誰待ちか」を出すための対応。どの状態がこちら待ちで、どれが相手待ちか。
# 状態は進み具合で、誰待ちとは別の軸なので、対応を設定で持つ。
waiting  = { new = "us", investigated = "them", in_progress = "us", done = "none", wont_do = "none" }

[approval_states]
values       = ["not_required", "pending", "approved", "rejected", "on_hold"]
# 承認が要る種別の初期値と、要らない種別の初期値。受け口がこれを入れる。
initial      = "pending"
initial_free = "not_required"
# 「保留」を表す値。hold_until を持てるのはこの状態のときだけ。
hold         = "on_hold"


# 画面に出す言葉。識別子 1 つにつき、言語ごとに 1 つ。
# ここに無い言語で開いた場合は、識別子をそのまま出す（黙って別の言語へ倒さない）。
[labels.ja]
bug = "不具合"
request = "要望"
question = "質問"
note = "メモ"
new = "未対応"
investigated = "調査完了"
in_progress = "対応中"
done = "完成"
wont_do = "対応しない"

[labels.en]
bug = "Bug"
request = "Request"
question = "Question"
note = "Note"
new = "New"
investigated = "Investigated"
in_progress = "In progress"
done = "Done"
wont_do = "Won't do"

[numbering]
# 接頭辞はアプリのリポジトリ名をそのまま使う。既に一意で、誰も新しく考えなくてよく、
# 接頭辞の登録簿も要らない。
# 保存した接頭辞は永久に変えない。製品名が変わったら、変えるのは表示名だけ。
display_names = { app_one = "Example Product", app_two = "Other Product" }

[database]
# 台帳は自分のデータベースを持つ。隣のサービスと同じところに間借りしない（§7）。
max_total_bytes = 0        # 0 は未設定。置く前に決める。固定の枠に閉じ込める
warn_at_percent = 80       # 枠のこの割合に達したら警告する

[attachments]
store = "webdav"
max_total_bytes = 0        # 0 は未設定。添付を有効にする前に実際の上限を入れる。
warn_at_percent = 80       # 添付の合計が上限の何 % に達したら警告するか。
fs_free_warn_bytes = 0     # ファイルシステムの空きがこれを切ったら警告する。0 は未設定。
max_file_bytes = 0         # 1 ファイルの上限。超えたら受け取らない。0 は未設定。

[attachments.retention]
# 起点は「案件が終端になった日時」。受信日ではない（§6）。
keep_days_after_closed = 0 # 0 は未設定。設定に持ち、コマンドの引数だけにしない。
batch_limit = 1000         # 1 回の実行で処理する上限。続きは次回へ回す。
tolerated_failures = 0     # 1 回の実行で、ここまでの失敗は正常とみなす。
```

**添付の上限と警告は、添付を有効にする前に入れる。後からではない。**

**`0`（未設定）のまま添付を有効にしようとしたら、起動を止める。**
無制限で動かすと、測る前に置いたことになる。**この節が言っているのはまさにそれをするな、なので、
設定を読む側がそれを強制する。**

- **空きをそのまま上限にしない。** 台帳は、台帳より大事なものと同じディスクに載ることが多い。
  同居しているものの伸びしろを残した値にする
- **合計を見る警告だけでは足りない。** `warn_at_percent` は添付の合計しか見ないので、
  **添付以外の理由でディスクが埋まる事故を捕まえられない**（置き場本体の増加、コンテナのイメージ、
  控えの置き場が同じディスクにある、など）。**ファイルシステムの空きそのものにも警告を 1 本置く**
- **上げるのは安全で、下げるのは既存の添付を消すことになる。** 迷ったら小さく始める

### 圧縮も再エンコードもしない

**添付は、送られてきたバイト列のまま保管する。**

- **画像には効かない。** JPEG と PNG は既に圧縮されているので、gzip をかけても普通は数 % も縮まず、
  場合によっては増える。**中身が zip の形式（表計算や文書のファイル）も同じ**
- 効くのは CSV・ログ・テキストのような未圧縮のもので、そこは大きく縮む。
  ただし**添付の中身の内訳を測るまで、どれだけ効くかは分からない。**
  効く割合が分からないうちは入れない
- 画像を本当に小さくするなら再エンコードだが、**バイト列が送られてきたものと変わる。**
  原則 4（台帳は保管する・加工しない）と正面からぶつかる。
  **証拠として添付を見る人にとっては、変わっていないことのほうが価値がある**
- **容量はまず上限とローテーションで管理する。** 圧縮を考えるのはその後で、
  実際に何が添付されているか見えてから

## 3. 受け口

### 受け口は 1 本

**人の報告も、アプリが検知した異常も、同じ 1 本で受ける。** 出どころは送る項目であって、
別の URL ではない。分けると取り決めが 2 本になり、検査も 2 か所になり、
**片方だけ直して食い違う余地が常に残る。** 検知したときにしか無い項目（指紋など）は、
人の報告では空のまま置く。

```
POST /v1/cases
Authorization: Bearer <token>
Content-Type: application/json
```

```json
{
  "origin": "human",
  "kind": "bug",
  "title": "月次シートが保存できない",
  "body": "保存を押すとページの先頭に戻り、何も保存されていない。",
  "reporter_ref": "u-10482",
  "tenant_ref": "tenant_a",
  "place": {
    "screen_id": "monthly-sheet",
    "feature_id": "save",
    "environment": "production",
    "version": "3.2.1",
    "url": "https://app.example.com/sheets/monthly"
  },
  "fingerprint": null,
  "legacy_ref": "1042",
  "promised_due": null
}
```

応答で、台帳が発行した番号を返す。

```json
{ "number": "app_one-234", "status": "new" }
```

**`source` は本文に書かない。**合言葉から決まる（§4）。本文に書かせると、
どのアプリでも他のアプリの接頭辞で採番できてしまう。

**`tenant_ref` は、合言葉の `tenant` が 1 つに決まっているときは省ける**（省くとその値が入る）。
`tenant` が `["*"]` のアプリ（顧客で分かれていない）では空になる。
**複数の顧客を持つ合言葉のときだけ、本文に書かないと決まらない。**

### 口の一覧

**案件は入れて終わりではない。**状態が変わり、承認が下り、返事を返し、証拠がぶら下がる。
**それぞれに口が要る。**書いていない口は、4 本のアプリがそれぞれ違う形で用意することになる。

| 口 | 何をする |
|---|---|
| `POST /v1/cases` | 案件を 1 件入れる。番号を返す |
| `GET /v1/cases` | 一覧。合言葉の範囲の中だけ（§4） |
| `GET /v1/cases/{number}` | 1 件 |
| `PATCH /v1/cases/{number}` | `status` ／ `approval_state` ／ `promised_due` ／ `hold_until` を変える。**変えたぶんは `case_events` に 1 行残る** |
| `POST /v1/cases/{number}/people` | 同じことに当たった人を 1 人足す |
| `POST /v1/cases/{number}/replies` | 返事を足す |
| `POST /v1/cases/{number}/links` | コミット・文書・URL を足す。**同じものを 2 回送っても 1 行** |
| `POST /v1/cases/{number}/attachments` | 添付を足す（下記） |
| `DELETE /v1/cases/{number}/attachments/{id}` | 添付の実体を消す。**行は残る**（§6） |

**承認もこの口を通る。**だから中央が止まっていれば承認もできず、その場で失敗が返る（下記）。

### 受け取りの細部

- **添付は、台帳へ送る。**アプリが置き場へ直接置く形にしない。
  **台帳が受け取ったバイト列から `sha256` を計算する**ので、保管したものが送られたものと
  同じであることを台帳自身が言える。アプリが計算した値を信じる形だと、受入条件 8 を誰も検証できない。
  案件と同じ要求で送ってもよいし、番号をもらってから足してもよい。
  **送る形は `multipart/form-data` で、部の名前は `file`。**台帳が返すのは
  `id` ／ `filename` ／ `mime` ／ `size_bytes` ／ `sha256`。
  **`sha256` は台帳が計算した値**なので、送った側はこれと自分の計算を突き合わせられる
- **題名が長すぎるものは、切らずに拒否する。**切るのは加工（原則 4）で、
  **送れなかったことを伝えるほうが、黙って中身を変えるより良い**
- **同じものを 2 回送っても 2 件にならない。**アプリが `legacy_ref`（自分側の ID）を付けて送れば、
  `(送り主, 元 ID)` で一意になる。**いちばん厄介なのは「送れたかどうか分からない」時で、
  人が書き直して送り直すと 2 件できる。**付けない送り主はこの守りを持てない
- **「同じこと」をまとめるのは、まとめる側の操作。**台帳が勝手に寄せない（原則 4）。
  2 件目だと分かっている報告は、新しい案件を作らず `people` の口へ送る。
  後から気づいたものは `duplicate_of` で指す。**指紋が同じ検知も、自動では寄せない。
  同じ指紋の行が並ぶのを許し、画面でまとめて見せる**

### 番号を発行するのは台帳

**アプリは番号を発行しない。台帳が発行する。** アプリは自分のローカルな識別子を持ったまま
`legacy_ref` として送り、人が口にする番号は応答で返ってくる。

これは見た目より効く。アプリは環境ごとに別のデータベースを持っていることが多く、
**アプリが自分で採番すると、検証と本番で同じ番号が別のものに付く。**
番号は案件を指すもので、**どこで見たかを指すものではない。どの環境で起きたかは既に列がある。**

中央で採番することで、下の受入条件が**何も作らずに成立する。**
**届かなければ番号が存在しないので、番号を表示しようがない。**

### 送れなかったとき

**アプリは、失敗したと本人に伝える。預からないし、「受け付けました」とも言わない。**

防いでいる事故がある。実際に起きたもので、画面と受け口が送る形について食い違い、
報告が全部拒否されていたのに、画面はその間ずっと「受け付けました」と表示していた。
**何も異常に見えないので誰も気づかなかった。** 1 本ではなく 4 本から送るようになれば、
同じ形が起きる機会はそのぶん増える。

預かって送り直す案（アプリが溜めて再送する）は、いちばん思いつく代案だが採らない。
書き直す手間は無くなるが、その代わりに**まだ受け取られていないものに「受け付けました」と
表示することになり、それは事故を起こした文そのもの。** さらに、確実に残る預かり場所、
再送の方針、再送が完全に失敗したことに気づく仕組みの 3 つが要る。
**正直なエラー表示 1 つを避けるために、静かに壊れうるものを 3 つ増やすことになる。**

したがって:

- 送信に失敗したら、**画面に失敗したと出す。**書いた文は画面に残し、書き直せるようにする
- **番号は出さない。**発行されていないから
- **受け付けられたように見えるのに台帳に無い、という状態が存在しない**

代償は実在するので書いておく。**台帳が止まっている間は誰も報告できない。**
これは目に見えて苦情の出る壊れ方であり、**静かな壊れ方よりこちらを選ぶ。**

§5 の承認の操作も同じ扱いにする。**承認も同じ経路で台帳へ届き、届かなければ失敗と出す。
預からない。**

### 案件とコミットの結び方

規約はコミットメッセージの末尾に 1 行。

```
Ref: app_one-234
```

**突き合わせはただの文字列一致。間にどんな道具も置かない。** そこが肝で、
台帳は番号の持ち主、バージョン管理はコミットメッセージの持ち主、
**どちらも相手の索引を持たない。** 索引は常に新鮮に保つ責任が発生するが、
**文字列一致には保つべき状態が無い。**

経路は 2 本あって、性質が逆になる。

| 向き | 手段 | 保存 | 性質 |
|---|---|---|---|
| 案件 → コミット | コミットメッセージを番号で検索する | しない | **常に最新。台帳が止まっていても引ける** |
| コミット → 案件 | `case_links` の行 | する | 速いが、**誰かが書かないと空のまま** |

**台帳の画面が使うのは、保存された行のほう。**「案件からコミットを検索する」経路は、
**開発者が手元で引くときのもの**で、台帳はリポジトリを持たないので実行できない（下記）。
2 つは競合しない。**手元では常に最新が引け、台帳では保存された行が見える。**

**同じコミットが 2 回送られてきても 1 行にしかならない。**`(案件, 種類, 参照)` で一意にしてある。
だから送る側は、取りこぼしが怖ければ何度でも送ってよい。

コミットが台帳へ届く経路も、案件と同じ。**リポジトリの複製を既に持っている側**
（開発者の手元、またはビルドの仕組み）が、同じ受け口へ送る。
**台帳はリポジトリを複製しないし、バージョン管理を実行しない。** 送られてきたものを保管するだけで、
これはこの文書の他のすべてと同じ形になっている。**台帳に誰かのソースを読む鍵を増やさずに済む。**

## 4. 合言葉と見える範囲

### 認証するのはアプリで、人ではない

台帳は**アプリ**を認証する。合言葉（ベアラトークン）と、必要なら送信元アドレスの制限。
**報告する人は認証しない。** 人は既にアプリへログインしていて、アプリが `reporter_ref` を
添えることで身元を保証する。

### 範囲は受け口の側で切る

4 本のアプリの案件が 1 つの表に入る。**あるアプリの画面が、別のアプリや別の顧客の案件を
表示しないことを、何かが保証しなければならない。**

**合言葉ごとに読める範囲を持たせ、受け口はその外を返さない。**
**呼ぶ側の画面が絞ってくれることを当てにしない。**

```toml
# 鍵・許可 IP・環境名。**doorpost が持つ表**（doorpost を使うサービスは同じ形）。
[[apps]]
name      = "app_one"
keys      = ["..."]
envs      = ["production", "staging"]
allow_ips = ["127.0.0.1"]

[[apps]]
name      = "app_two"
keys      = ["..."]
envs      = ["production"]
allow_ips = ["203.0.113.0/24"]

[[apps]]
# 横断で見る画面。運営側のみ。
name      = "operator_console"
keys      = ["..."]
envs      = ["production"]
allow_ips = ["127.0.0.1"]

# 見える範囲。**issuepost だけが持つ表。**[[apps]] の name で結ぶ。
[[scopes]]
app    = "app_one"
source = ["app_one"]
tenant = ["tenant_a"]

[[scopes]]
app    = "app_two"
source = ["app_two"]
tenant = ["*"]        # 顧客で分かれていないアプリ

[[scopes]]
app    = "operator_console"
source = ["*"]
tenant = ["*"]
```

**`source` と `tenant` は必ず配列で書く。**「全部」は `["*"]`。
片方を文字列、片方を配列にすると、読む実装が 2 通りになる。

### なぜ 1 つの表にまとめないか（2026-09-12 決定）

**鍵・許可 IP・環境名を持つのは `doorpost` で、issuepost ではない。**
同じ形を、doorpost を使う他のサービスも使う。**受け口を持つサービスで
設定の書き方を揃えるのが目的**なので、issuepost だけが `[[tokens]]` という
別の綴りを持つ形は採らない。

doorpost は**知らないキーがあると起動しない**（綴りを間違えたときに黙って既定値で
動き出さないため）。`[[tokens]]` を足すと、そもそも起動しない。

**見える範囲は issuepost にしか無い概念**なので、`[[scopes]]` として別の表に置き、
`name` で結ぶ。**持ち主が違うものを同じ表に書かない。**こうしておくと、
doorpost 側だけを後から直せる。

**書き忘れは起動時に落ちる。**`[[apps]]` に対応する `[[scopes]]` が無ければ起動しない
（**無い＝全部見える、とは読まない**）。逆に、対応する `[[apps]]` の無い `[[scopes]]` も
起動しない。**2 つの表に割ったことで生まれる「片方だけ書いた」を、起動時に潰す。**

### 顧客の軸は、アプリの軸だけでは足りない

**1 本のアプリを複数の顧客が使う構成では、`source` で切っても足りない。**
同じアプリの中で顧客 A と顧客 B の案件が混ざり、**顧客 A の画面に顧客 B の案件が出る。**
これは下で代案を却下した理由とまったく同じ事故なので、こちらの案でも防ぐ。

だから案件は `tenant_ref` を持ち、**合言葉は `source` と `tenant` の両方で範囲を切る。**
`tenant_ref` は、アプリが既に持っている顧客の識別子をそのまま入れるただの文字列で、
外部キーは張らない（`reporter_ref` と同じ扱い）。

**顧客で分かれていないアプリは空にする。**その場合、合言葉の `tenant` は `["*"]` になる。

代案（台帳は全部返し、画面の側で絞る）は採らない。**保証が、次に画面を書く人の手に移る。**
条件を 1 か所書き忘れると、ある顧客に別の顧客の案件がそのまま出る。
**これは、やってしまってから気づく種類の間違い**なので、テストで拾う対象ではなく、
起きない形に設計する対象。受け口で切っておけば、**絞り忘れた画面はただ何も余計に受け取らない**し、
画面を増やしても露出は広がらない。

両方でやる（受け口で切ったうえで画面でも絞る）も採らない。理由は 1 つだけ。
**同じ条件が 2 か所にあると、変えるときにどちらが正か分からなくなる。**

### 合言葉そのものの扱い

- **入れ替えられるようにする。**新旧を同時に有効にできる期間を設けないと、
  入れ替えが 4 本の同時停止になる。**実装済み**（`keys` は 1 アプリ 2 本まで持てる）
- **本番と検証で別の合言葉にする。**どちらも 4 本ぶんあるので、最初から数が増える前提で作る
- **設定に置くのは合言葉のハッシュ。**そのままの値を置かない。
  設定ファイルは控えにも入り、覗ける人の範囲が広い。
  **未実装**（下記）
- **失効に再起動を要らなくする。**漏れたときに待てない。**未実装**（下記）

**下の 2 つは、いまは作らない**（2026-09-12 決定）。

どちらも doorpost 側の話で、doorpost にハッシュの口も読み直しの口も無い。
比較は素の値どうしを `crypto/subtle.ConstantTimeCompare` で行っている
（合っていたかが所要時間に出ないように）。

**いま足しても守る相手が増えない。**鍵を知りうるのは運用の 3 名だけで、
サーバーは SSH 専用・IP 固定・鍵認証のみ（パスワード認証なし）。
設定ファイルは `0640` でサービス専用ユーザーに閉じる。
**設定ファイルを覗ける人と、サーバーへ入れる人が同じ**なので、
ハッシュにしても、そのハッシュを置いたファイルを読める人が同じだけ残る。

**効き始めるのは、運用が 4 人目へ広がるか、設定の控えが外の保管先へ出るとき。**
その段で doorpost へ足す（**issuepost だけに足さない。**3 本で同じ形にするのが主題）。

### 接頭辞が衝突したとき

接頭辞はリポジトリ名をそのまま使う（§2）。**登録簿を作らないための工夫**だが、
組織をまたぐと同名のリポジトリは存在しうる。**同名が来ると番号が混ざる。**

実際には、合言葉が `source` を固定する（上記）ので、**知らない接頭辞が勝手に採番されることはない。**
合言葉を作る操作が、事実上の登録になっている。衝突したら、**後から来たほうの `source` に
接尾辞を付けて区別する**（保存した接頭辞は変えないという規則は、既存のほうに効く）。

### 顧客ごとの分身は作らない

顧客ごとに台帳を置く形は作らない。**分身の数だけ同じ種類の記録の持ち主が増える**し、
運営側は横断して見るために結局中央のものが要るので、**2 か所を突き合わせ続けることになる。**
そのうえ複製をどちら向きに流すかを決める話になる。**案件を 1 か所に置くと決めたことが、
実質的に取り消される。**

分身を置きたくなる元の動機（顧客側の人が台帳へ到達できない）は、ここでは起きない。
**運営側の外にいる人は、そもそも台帳へ接続しない。** 本人の代わりにアプリが、
サーバー同士で取りに行く。

## 5. 画面

### アプリの中 — 運営側の外にいる人が作業する場所

**報告を書く画面は各アプリの中にあり、そこにしかない。台帳には報告画面を置かない。**

理由は発生場所の項目。**問題が起きた画面からそのまま書けば、画面・版・環境が自動で付く。**
中央の 1 枚に集めると、誰かがそれを一覧から選ぶことになり、**選ばれなかった画面は数字から
消える。**「どの画面が一番トラブルを集めているか」も一緒に消える。

各アプリが持つもの:

- **報告の入力**。問題が起きているその画面の上に置く
- **一覧と詳細**。そのアプリの案件だけ。番号・状態・誰待ちかを出す
- **承認の操作**。承認が要る種別に対して。
  **承認するのはそのアプリの中にいる利用者管理者で、他のアプリのことは知らないし、
  そのために別の画面へ移らせない**
- **4 枚のパネル**（下記）。そのアプリのぶんだけ

### 台帳の中 — 運営側が横断して見る場所

運営側の開発者と経営層は、台帳自身の画面で全部を見る。**同じ 4 枚を 4 本ぶん合算したもの**と、
**アプリ別に内訳を出す 1 枚**。最後の 1 枚は定義上、運営側だけのもの。
**組織をまたいだ比較なので、顧客向けの画面には出せない。**

### 4 枚のパネル

**見て次にやることが決まる数字だけを置く。何も決まらない数字はパネルにしない。**

**数える範囲は 4 枚とも同じ。**設定の `open` に入っている状態の案件だけを、期間で区切らずに数える。
**揃えないと、同じ画面の数字がアプリごとに違う意味になる。**
「誰待ちか」は `status` そのものではなく、設定の `waiting` で引いた値で分ける
（進み具合と誰待ちは別の軸なので）。

| パネル | 何が分かるか | それを見て何をするか |
|---|---|---|
| 期限を過ぎた | 約束した期日を過ぎた件がある | 今日どれから手を付けるか。**ここが 0 なら、今日は他のことをしてよい** |
| 誰待ちで止まっているか | 止まっているのがこちらか、相手か | 催促するか、自分が動くか。**業務側に積もっていたら、まとめて 1 回聞く** |
| どの画面で起きているか | 1 つの画面に集中していれば、その画面自体が弱い | 個別に直すか、画面ごと作り直すか |
| 種類の比率 | 不具合か、要望か、質問か | **手当てのしかたが変わる。質問が多い画面は、コードではなく言葉が悪い** |

残り 2 枚は後から作る価値があるが、最初には入れない。**同じことを言っている人数**と、
**最初の回答までの日数**。
（**アプリ別の内訳は最初から作る。**運営側の画面にだけ置く 5 枚目）

### 承認 — 操作はアプリ、状態は台帳

**承認の状態は台帳が持つ。** そうすると運営側が、4 本ぶんの「業務の判断待ち」を
1 つの一覧で見られるし、**承認の履歴が案件と同じ場所に残る。**

**誰が承認できるかの名簿はアプリ側に残す。** アプリは既にそれを持っていて、
誰がログインしているかも知っている。**台帳へ写すと、人の出入りのたびに 2 か所を直すことになる。**

### 直した証拠

**終端にしたのに `case_links` が 1 件も無い案件には、一覧に「証拠なし」の印を出す。**
コミットは複製を持っている側が受け口へ送ってくる（§3）ので、**規約どおり直せば行が入る。**
行が 1 つも無いのは、送る仕組みが動いていないか、`Ref:` の書き忘れか、そもそも直していないか。
通知ではなく、**人がもともと見ている画面の上の印**にする。週 1 の通知を増やしても読まれないし、
一覧の印なら、そこで作業している人が自然に気づく。

## 受入条件

参照実装は、これが全部成り立つまで完成ではない。

1. **送れなかったものが、受け付けたように見えない。** 預かりも、先走った表示も、
   案件が保存されていないのに出る番号も無い
2. **番号は案件を指し、環境を指さない。** 同じ案件を 2 つの環境で見ても番号は 1 つ
3. **台帳が、どのアプリのテーブルにも外部キーを張っていない。**
   他のシステムを引きずらずに、まるごと別の場所へ移せる
4. **合言葉は、自分の範囲の外を読めない。** 呼ぶ側の画面が何を要求しても変わらない
5. **保存した接頭辞が変わらない。** 製品名が変わっても変えるのは表示名だけで、
   既存の番号と、それを引用しているコミットメッセージが生き続ける
6. **保存されているのが識別子で、画面の言葉ではない。** 表示名を変えても、
   保存された値も集計も動かない。**表示名を翻訳しても、保存される値は 1 つのまま**
7. **台帳は受け取ったものを保管している。** 分類し直しも書き換えもしていない
8. **添付は参照である。** データベースにもリポジトリにも、中身そのものが入っていない。
   **保管されているバイト列は、送られてきたものと同一**（圧縮も再エンコードもしていない）
9. **組織固有の値がすべて設定にある。** 取得したばかりの状態に、実在の状態名・種別・
   接頭辞・表示名が 1 つも入っていない
10. **添付を消しても、消えたことと理由が残る。** 行が消えず、ハッシュも残り、
    「期限で消した」「人が消した」「置き場に無かった」が区別できる。
    **案件そのものが消せない**ので、行ごと消える経路が無い
11. **削除済みの印を、一覧・取り出し・定期の抽出の 3 か所が読んでいる。**
    **どれか 1 つでも読んでいないなら、添付を有効にしない**
12. **定期実行が実際に登録され、動いていることを確認した。**
    **仕組みを作っただけでは動かない。**「実装したから消えているはず」を根拠にしない。
    確認の根拠は `cleanup_runs` の行
13. **1 本のアプリを複数の顧客が使っても、顧客をまたいで見えない。**
    合言葉が `source` と `tenant` の両方で範囲を切っている
14. **状態と承認の移り変わりが残っている。** いまの値を上書きしても、
    誰がいつ何から何へ変えたかを後から言える
15. **同じものを 2 回送っても 2 件にならない**（送り主が自分側の ID を付けている場合）
16. **日時がすべて UTC で保存されている。** サーバと接続のタイムゾーンが UTC に固定してあり、
    **「期限を過ぎた」の境界が見る場所でずれない**
17. **台帳が太っても、隣のサービスが道連れにならない。** 容量・メモリ・CPU に枠が掛かっていて、
    **枠を超えたとき止まるのは台帳だけ**
18. **台帳のデータベースの控えが、自分の仕組みで取れている。**
    隣の控えに相乗りしていない。**時刻が隣の控えと重なっていない**
19. **データベースをマシンの外へ出していない。** 台帳からだけ届く経路に置いてある
20. **版を固定したうえで、いつ誰が上げるかが手順に書いてある。**
    **固定しただけで放置すると、古いまま動き続ける**

## 6. 添付の寿命

**台帳は実体を持たない**（§1）。持っているのは参照とメタだけ。だから「消える」には向きが 2 つある。

- **台帳が期限だと判断し、置き場へ消させる**
- **置き場の側で先に消えている**（台帳の知らないところで）

**どちらも起きる前提で作る。** 後者を考えていない作りは、参照が死んでいることに気づけない。

### 消えても、消えたことが残る

**実体が消えても行は消さない。** 残すのは、元のファイル名・種類・サイズ・内容のハッシュ・参照・
**いつ消えたか・なぜ消えたか**（§1 の `case_attachments`）。

**ハッシュは消さない。** 同じファイルが後からもう一度来たときの判定が、これだけで成立する。
**実体を消す判断と、メタを消す判断を、同じ操作にまとめない。**

**理由を持つ。** 消えた日時を 1 本だけ持つと、**「期限で消した」「人が消した」「置き場に元から無かった」が
全部同じ形になり、後から「なぜ消えたのか」に答えられない。**

| 理由 | いつ付くか |
|---|---|
| `expired` | 期限が来て、台帳が消させた |
| `removed_by_user` | 人が消した |
| `missing_at_store` | 消しに行ったら、置き場に無かった |

**`missing_at_store` でも印は付ける。** 付けないと、次の実行でまた同じ行を見に行く。
**置き場は台帳の知らないところで消えることがあるので、ここが効く。**

### 期限の起点は「案件が終端になってから」

**受信日からの日数にしない。** それだと**未解決のまま時間が経った案件の添付が消える。**
「誰待ちで止まっているか」を見る台帳では、**古い未解決こそ見たいもの。**

だから起点は `closed_at`（案件が終端状態になった日時）。**これを最初から持つ**（§1）。
後から「終端から N 日」へ変えたくなったとき、**起点が無いと過去のぶんを埋められない。**

### 保持日数は設定に持つ

**コマンドの引数だけにしない。** 引数だけだと、付けた実行と付けない実行が混ざり、
**何日保持なのかが実行履歴にしか残らない。** 設定に既定を置き、引数は一時的な上書きに留める。

### 消し方は 2 段構え

- **即時**: 人が消したとき、その場で置き場へ消させる。**失敗しても記録は進める**
  （理由と日時を入れる）。落ちたぶんは定期のほうが拾う
- **定期**: 期限の来たものを拾う。**即時が失敗したぶんも同じ経路で回収される**

この形なら、**片方が落ちてももう片方が直す。**

### 印を読む側も、同時に決める

**印を書く仕組みだけ作って読む側を決めないと、静かに壊れる。** 行は一覧に出たまま、
開くと「ファイルが見つかりません」になり、**利用者からは「期限切れで消えた」と
「そもそも無かった」が区別できない。**

読むのは 3 か所。**3 つとも決まってから有効にする。**

| どこ | どう扱うか |
|---|---|
| 一覧・詳細 | **行は残し、「期限切れで削除済み」と理由つきで見せる。**消して無かったことにしない |
| 取り出し | **見つかりませんではなく、消えた理由と日時を返す** |
| 定期の抽出 | 走査の対象から外す |

### 上限に当たったら、受け付けない

**古いものから押し出さない。押し出すと、まだ必要なものが消える。**
上限に当たったら**添付の受け付けを止め、そう表示する。** §3 の「送れなかったら、そう言う」と同じ。

**ただし案件そのものは受け付ける。** 添付が付かないだけで、報告は台帳に入る。
**添付が入らないことを理由に案件を落とすほうが、損失が大きい。**

### 定期実行は、作っただけでは動かない

**仕組みを作っても、動かす登録は別の作業。**
「実装した日から消えている」と思い込むのがいちばん危ない。**受入条件に入れる。**

### 数えるところ

- **空実行（dry-run）を最初から持つ。** 対象の件数と合計サイズを出す。
  **有効にする前に見積もれる**
- **空実行と本実行で、同じ名前の数字は同じ意味にする。** 片方が「消す予定の数」で
  もう片方が「消えた数」だと、**ずれても誰も気づかない**
- **1 回の処理量に上限を置き、続きは次回へ回す。**
  ただし**上限と実行間隔の関係を決める。** 溜まっている量が 1 回の上限を超え続けると、
  **永久に追いつかない**
- **失敗が何件までなら正常かを決める。** 1 件の権限エラーで毎回赤くなると、**監視が無視される**

### 参照を外から受け取るときの検証

置き場が返す取得先を外から受け取る場合、**問い合わせた先と同じ相手でなければ採用しない**
（方式・ホスト・ポートの一致）。**転送（リダイレクト）も追わない。**
参照を外から受け取る設計には、この検証が必ず要る。

## 7. 置き方

**台帳は、たいてい「すでに何かが載っているマシン」へ足すことになる。**
だからこの節は、台帳をどう作るかではなく、**隣にいるものを巻き込まない置き方**を決める。

### 方針: 物理は諦め、それ以外は断つ

マシンが落ちる、マシンを再起動する。**ここは巻き込まれてよい。**同じ鉄の上にいる以上、
避けようとすると台数を増やす話になる。

**それ以外の繋がりは、1 つずつ断つ。**断てるのに断っていないものは、後で必ず効いてくる。

| 繋がり | どう断つか |
|---|---|
| 版・パッケージ | **データベースを自分のものとして持ち、版を自分で固定する。**隣の都合で上がらない |
| プロセス・設定・再起動 | 同上。**こちらだけ落として戻せる**状態にする |
| 接続数 | 自分のインスタンスなので独立。上限も自分で決める |
| メモリ・CPU | **上限を掛ける。**掛けないと、太ったときにマシンをスワップへ押し込んで隣を遅くする |
| ディスクの容量 | **固定の枠に閉じ込める**（下記）。埋めても、外の空きは減らない |
| ディスクの IO | 優先順位を下げる。完全には切れない |
| ポート | **データベースをマシンの外へ出さない。**台帳からだけ届く経路に置く |
| 控え | **自分で 1 本持つ。**隣の控えに相乗りしない（下記） |
| ログ | 自分の置き場へ出し、サイズの上限を掛ける |
| 前段（HTTP を受けるもの） | **共有してよい。**ただし独立した名前で（下記） |

### データベースは自分のものを持つ

**隣のサービスのデータベースに間借りしない。**同じところに置くと、上の表の上から 5 つが
まとめて繋がったままになる。とくに効くのが 2 つ。

- **版が隣の都合で上がる。**そして多くのデータベースは、上げたデータを古い版では読めない。
  **戻せない。**
- **こちらの都合で止めるときに、隣を止めることになる。**設定の変更、詰まった問い合わせ、
  移行のための再起動。**小さいほうが大きいほうを止める形**になる

**版を自分で固定するということは、更新を自分で面倒見るということ。**
固定したまま誰も触らなければ、古いまま動き続ける。**いつ誰が上げるかを手順に書く。**

### 容量は固定の枠に閉じ込める

**マシンのファイルシステムが 1 つしかないことは珍しくない。**その場合、台帳が太れば
隣が道連れになる。**固定サイズの領域を用意して、その中だけを使う。**
上限を超えたら台帳だけが書けなくなり、外の空きは減らない。

添付の上限（§6）とは別枠。**添付を止めても、案件と履歴は増え続ける**ので、両方に枠が要る。

**履歴の表は追記だけで消さない。**経緯を消さないと決めた以上、そこは崩さない。
増え方は案件の数に比例する（1 件あたり数行）ので、**消すのではなく、枠と警告で見張る。**
枠に近づいたら、消すのではなく移す（別の場所へ書き出す）ことを考える。

### 控えは自分で持つ

**隣の控えに相乗りしない。**多くの控えは対象を名指しで取る形なので、
**新しいデータベースは自動では入らない。**「分けたのに控えが無い」が、いちばん危ない状態。

時刻は隣の控えとずらす。**同じ時間帯に重ねると、ディスクの取り合いで両方遅くなる。**
定期の片づけ（§6）も、控えの時間帯を避ける。

### 前段は共有してよい。ただし独立した名前で

HTTP を受けて証明書を持つものは、共有してよい。**証明書の更新は回っている仕組みに乗るほうが、
止まったときに気づく人がいる。**自前でもう 1 系統持つと、更新が止まっても誰も見ない。

ただし**独立した名前（ホスト名）で出す。**既存の入口にパスで相乗りさせない。

- 相乗りさせると、**他のアプリの振り分け規則と当たる**
- 後で別のマシンへ移すとき、**名前で出していれば向き先を変えるだけで済む**
- 送る側の 4 本にとっても、宛先が 1 つの名前で完結する

**前段の設定を間違えると、検査に落ちて読み込み直しが全体で止まる。**
設定を配る前に検査し、落ちたら戻す形にしておく。

### 置く前に登録するもの

**実装より先に、台帳に 1 行ずつ書く。**後から書くと、必ず書き忘れる。

- 使う待受の番号（マシンの中で重複しないこと）
- 定期実行の時刻（既存のものと重ならないこと）
- 控えの対象（新しいデータベースを対象へ足したこと）
- サービスの一覧（このマシンで何が動いているかの記録）

## 置く前に確かめること

設定に書く値は、実際に置くマシンを見てからでないと決まらない。**先に決められるのは
「何を確かめるか」だけ**なので、それをここに書く。**どれも推測で埋めない。**

### 1. 空きと、同居しているもの

`df` で、置き場が載っているファイルシステムの空きを取る。**同じディスクに何が同居しているかも
一緒に見る**（置き場の本体、データベース、コンテナのイメージ、控えの置き場）。
その全部の伸びしろを残した値を `max_total_bytes` にする。**空きの全部を渡さない。**

`fs_free_warn_bytes` は、そのファイルシステムの空きに対して設定する。
**添付の合計に対する警告とは別物で、両方要る。**

### 2. 控えが、本当に取られているか

**「ファイル置き場なのだから控えは取られているはず」と仮定しない。確かめる。**
確かめる先は 3 つ。

- 定期実行の仕組み（cron の登録、systemd のタイマー）に、控えを取るものがあるか
- 控えを取る道具が入っているか
- **それぞれが何を対象にしているか。**「動いている」と「必要なものを含んでいる」は別

結果は 3 通りあり、それぞれ違う判断になる。

| 確かめた結果 | どうするか |
|---|---|
| ファイル置き場が控えの対象に入っている | 添付はそれに乗る。**データベースは下の 3 を見る** |
| ファイル置き場が対象に入っていない | **添付は控えの無いものとして扱う。**添付を有効にする前に、控えを足すか、失ってよいと決めるか、どちらかをはっきりさせる |
| 控えが同じ 1 台の同じディスクにだけある | ディスクごと失うと控えも一緒に消える。**外へ出すかどうかを決める** |

### 3. 台帳のデータベースの控えは、別に用意する

**既にデータベースの控えを取る仕組みがあっても、台帳のぶんが自動で含まれるとは限らない。**
よくある形は、対象のデータベースを名指しして取るもので、**新しいデータベースを足しても
名指しの一覧に入らない限り含まれない。**

確かめること: 既存の仕組みが**全部を取る形か、名指しの形か。** 名指しなら、
台帳のぶんを一覧へ足すか、同じ形の仕組みをもう 1 本置く。

**4 本ぶんの経緯がここに集まるので、失うと全部消える。**

## まだ決めていないこと

- **返信を報告者へ届ける書き方。** 既存のチャットに 1 行流して詳細は台帳で見てもらう、
  という経路を想定しているが、宛先の指定方法が固まっていない。
  **届いたかどうかを持つ列は用意してある**（§1 の `case_replies`）
- **個人情報の削除を求められたときの扱い。** 案件は消さない形にしてあるので、
  本文や `reporter_ref` を伏せる操作が別に要る。**消すのか、伏せるのか、伏せたことを残すのか**が未定
- **`fs_free_warn_bytes` と `max_file_bytes` の値**、および
  **定期実行の間隔と `batch_limit` の関係**（§6 が「決める」と言っている 3 つ）
